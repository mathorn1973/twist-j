# NON-CANONICAL: erratum for the Public Canon v29 release

This note is not canon. It edits no file under `canon/`, changes no claim,
status or scope, and carries no status of its own. It records a process failure
in the v29 release so that the failure is public rather than quiet.

## The fact

The tag `canon-v29` is immutable and points at merge commit
`607b3e587ec55acc91fd9c61947d600e1cdabc53`. The tree at that tag **does not
pass** the full activation readback. Pushing the tag ran the publication
workflow, which failed:

```text
run 30629417385, tag canon-v29
FAIL: status-separation exits 1
ACTIVATION MANIFEST ...
ACTIVATION BLOCKED blockers=1
```

No release assets were published for v29, because `AGENTS.md` section 6 item 9
permits assets only after the tag readback passes. It did not pass, so there
are none.

## The cause

`reproduce/status-separation/verify.py` hard-codes the size and the status
partition of the registry: `len(rows) == 215` and
`expected_counts = {"T": 114, "D": 40, "C": 23, ...}`. The v29 fold moved the
registry to 216 claims with `C` at 24. Gate `01 COUNTS` of that reproduction
therefore failed, 16 of 17, and the reproduction exited 1.

The fixture was correct for v28 and stale for v29. The v28 fold updated it in
the same commit as the Canon change; the v29 fold did not.

## Why no gate caught it before the tag

`tools/check_reproduce.py --base` reproduces only the directories under
`reproduce/` that appear in the pull-request diff. The v29 fold changed files
under `canon/` and one test under `tools/`, and no directory under `reproduce/`,
so the pull-request gate printed `REPRODUCE NOT APPLICABLE` and never executed
the fixture. The complete sweep of every reproduction runs only in
`tools/check_activation.py --full`, which the workflow invokes on tag and
release events.

There is therefore a window in which a Canon change invalidates an unchanged
reproduction fixture, passes every gate a pull request can run, and fails only
after the tag is public and immutable. The `protect-canon-releases` ruleset
blocks deletion, non-fast-forward and update on `refs/tags/canon-v*`, so the
failing tag cannot be moved or withdrawn.

## What is and is not affected

Not affected. The Canon content itself is sound at v29 and was verified from a
fresh public clone before the tag was pushed: `SHA256SUMS` matches all five
hashed files, `STATUS.md` agrees with the tree on `CANON_SHA256` and
`CANON_BYTES`, `CONTENT_COMMIT` is an ancestor, and `check_canon.py`,
`check_ledger.py` and `check_policy.py` all pass, as do the 59 unit tests. The
registered claim `ENTROPY-RG-RETURN [C]`, its scope hash, its evidence bundle
hash and its history row are unchanged by this erratum.

Affected. The tag `canon-v29` will always fail
`tools/check_activation.py --full` on the tree it names, and v29 has no
published release assets.

## What was done

The fixture was corrected on `main` after the tag, in the pull request that
carries this note. The correction changes `reproduce/status-separation/` only:
the two hard-coded counts, the gate label, and `EXPECTED.txt` regenerated by
running the corrected verifier. Nothing under `canon/` moves, `CANON.md` and
`SHA256SUMS` are byte-identical, and no new Canon integer is spent, because the
Canon content is not what was wrong.

The tag is left in place. Cutting a further release to obtain a tag whose
readback passes was considered and rejected: it would spend a Canon integer on
an accounting fixture and would misrepresent a tooling failure as a change in
the Canon.

## Open

The gate window above is not closed by this note. The smallest correction is to
run the complete reproduction sweep whenever a pull request touches
`canon/REGISTRY.tsv`, rather than only the reproductions the diff names. That is
a change to a gate and belongs in its own reviewed pull request under the rule
in `AGENTS.md` section 6 that workflows are not loosened or altered without an
explicit policy change.
