## 3. F-watch procedure (one page, run at every status update)

The rule (status page section 1; patch proposal section 3): a rigorously
established nontrivial zero of `zeta(s)` with `Re(s) != 1/2`, in an
independent public record by exact enclosure or machine-checked proof, is a
program falsifier. A claim is STOP, not `F`. An external proof of RH promotes
nothing.

**Step 0. Gate.** Read `STATUS.md`, confirm STATE ACTIVE and the declared
Canon tag. Write the date and Canon version at the top of the watch record.

**Step 1. Scan.** Run at least these queries and record for each: query text,
reachable or unreachable, finding in the closed vocabulary
`NONE / CLAIM-ONLY / T-DIRECTION / RECORD / BLOCKED`, where `CLAIM-ONLY` is
reserved for a disproof claim (an off-line zero asserted without a record),
and an unconfirmed proof-direction claim files as `NONE` with an annotation
(step 4). Record rows as attempts; count distinct unreachable hosts
separately.
(a) off-critical zero, current year; (b) RH proof with Lean/Coq/Isabelle
certificate, current year; (c) verified height beyond `3*10^12` rigorous;
(d) arXiv listing for "Riemann hypothesis", current month, claims of proof or
disproof. Try a direct arXiv fetch every time and record the block if it
persists. Never fill an unreachable source from memory. Save the raw search
and fetch output next to the record when the environment allows it; when it
does not, say that the table is hand-typed.

**Step 2. Classify every item that claims an off-line zero.** It is a
RECORD only if all of the following hold; otherwise it is CLAIM-ONLY.
1. Independent: authored outside TWIST-J and outside any fleet run of this
   program; public at a stable citable location (journal, arXiv with
   identifier, or a public repository with a commit hash). A private
   message, a blog summary, a search-engine summary, or a screenshot is not
   a record.
2. Exact enclosure, if numerical: a box `[a1, a2] x [b1, b2]` with rational
   endpoints, lying inside the open strip `0 < a1 < a2 < 1` (so that any zero
   it contains is nontrivial), with `1/2` outside `[a1, a2]`, plus an
   argument-principle or interval-Newton certificate that the box contains
   exactly one zero of `zeta` (equivalently of `xi`, which has the same zeros
   in the strip), with every intermediate quantity carried as a rigorous
   interval (or ball) and the rounding mode stated. The certificate must name
   the method and its published error analysis, and the box must be
   reproducible from the stated inputs alone. A floating-point table of
   "zeros" is not a record: a printed value `1/2 + 10^-9 + i t` carries no
   statement about what lies inside any box, no bound on rounding, and no
   proof that the counted object is a zero rather than a near-cancellation;
   the same table can be produced with `Re = 1/2` by a different rounding
   choice. Only an enclosure separates a zero from the line. (The strip
   condition was missing in the first version of this page; without it a box
   around the trivial zero `s = -2` passed the item. Verifier check 7 tests
   the corrected shape condition exactly.)
3. Machine-checked proof, if symbolic: a Lean/Coq/Isabelle development that
   states the existence of `s` with `zeta(s) = 0`, `0 < Re(s) < 1`,
   `Re(s) != 1/2`, against the library's own `zeta`, with no `sorry`, no
   added axioms beyond the library's, no `True := trivial` stubs on the
   path, and a stated checker version. A conditional theorem is not a proof.
4. Reproduced: the program has rerun the enclosure (exact rational interval
   arithmetic is enough for a box check) or rebuilt the Lean project from
   the named commit and obtained the same result. Until reproduced, STOP.

**Step 3. Two actions, no third.**
- CLAIM (any item failing one or more of 1-4): file STOP. Record the item,
  the failing conditions, and nothing else. No row moves, no `F`, no note in
  the changelog, no "likely" language. Re-examine at the next update only if
  the item changed.
- RECORD (all of 1-4): the falsifier of `RH-PROGRAM-DEPENDENCE` fires (once
  that row exists) and by the declaration of 2026-09-08 the program halts.
  The fold is an owner fold: cite the record by identifier and commit, attach
  the program's own reproduction, and mark `LAMBDA-COCYCLE-ANGLES [H]` fired
  through its "RH disproved" clause in the same fold. Nothing else is
  derived on that day.

**Step 4. Proof claims (the other direction).** Classify as in step 2 items
3-4 for completeness of the record only. A confirmed proof retires the
dependency row to the changelog with the citation and changes no other row
(patch proposal section 7). An unconfirmed proof is not even STOP; it is
`NONE` for the watch, annotated as a proof-direction claim in the source
table so the datum is not lost.

**Step 5. Close.** Run `verify_f_watch.py` with the source table updated and
the STOP-filed list matching the record, keep its stdout next to the record,
and write the final line verbatim. If arXiv is still blocked, say so in the
first verdict row.

## 4. Verifier

`verify_f_watch.py`: Python 3 standard library, `int` and
`fractions.Fraction` only, no floating point, deterministic under
`LC_ALL=C PYTHONHASHSEED=0`. It prints the date, the 23 attempts (rows) with
reachable/unreachable and finding, seven PASS/FAIL lines,
`CHECKS: 7 of 7 PASS`, and the final line
`F-WATCH: no record of an off-critical zero found in the reachable sources`.
Exit 0. Runtime under one second. The checks are:

1. closed vocabulary;
2. unreachable equals BLOCKED;
3. exact counts: 23 attempts, 12 reachable, 11 unreachable, 10 distinct
   unreachable hosts (3 arXiv, 7 other);
4. no RECORD among reachable rows;
5. the CLAIM-ONLY rows are exactly the rows filed STOP in section 2 (one
   row, Liu 2404.06306); the check passes with zero rows on a clean watch;
6. the arXiv block is recorded;
7. the corrected item-2 box condition, evaluated in exact rationals, rejects
   the trivial-zero box `[-21/10, -19/10] x [-1/10, 1/10]`, rejects a box
   straddling `Re(s) = 1/2`, and admits the shape of a strip box with `1/2`
   outside its real range. This is a shape test; it asserts nothing about
   where any zero lies.

The source table is hand-typed from the session's search and fetch output,
which is not saved in the lane directory. Checks 1-6 are consistency checks
on that table and cannot fail because the scan was wrong; check 7 tests one
sentence of the checklist. The verifier checks nothing about `zeta(s)`, by
design. Saved stdout: `verify_f_watch.stdout`.

## 5. What this does not do

- It does not verify, enclose, or compute any zero of `zeta(s)`; the watch
  is bookkeeping and the verifier asserts nothing about zeta.
- It does not read arXiv. The September 2026 listing is unscanned; the
  scan is partial and says so in every place it matters. It does not claim
  to have exhausted the reachable search space either: a referee's own
  query surfaced a March 2026 proof claim (2603.05122) this lane had not
  listed; `NONE` under step 4, not added to the table (Review record B1).
- It does not treat search-engine summaries as records; the summaries are
  unconfirmed characterisations, and the one date discrepancy it noticed
  (Fayed 2209.01890) is left unresolved rather than "corrected".
- It does not certify the scan by verifier: the verifier certifies a
  hand-typed table and one shape test.
- It does not move any row, does not use the letters `T`, `C` or `F` for
  any result of its own, and does not read the Alpoge-Furman or Lamzouri
  proportion results as evidence for or against RH.
- It does not invoke the counting rule of RH-ONE-WALL-CROSSREF_2026-08-17.md
  because it proves nothing to count; it only notes that the GPPVerify
  conditional statement has the shape of the known wall and is not a new
  level.
- It does not decide any of the three owner decisions of the patch proposal.
